# Дизайн

## Контекст

См. proposal.md — зачем. Пайплайн перевода (change `translation-pipeline`, архив) уже умеет: LLM-перевод файла целиком (`tools/translate.mjs`), детерминированную валидацию (`tools/validate-translation.mjs`, покрывает `.ts`/`.tsx` и markdown), фиксацию статусов (`tools/mark-translated.mjs`, шкала `pending → machine → reviewed`). Дизайн того change прямо постулировал: «`machine → reviewed` проставляет только человек». Это изменение отменяет то решение — `reviewed` теперь может проставлять инструмент после ревью advisor-моделью.

Проверка advisor'ом (критический разбор плана) выявила два ограничения, которые формируют подход:

- Regex-валидатор для `.tsx` проверяет только `${...}`-токены и имена import/const/export. Он не парсит JSX и не ловит сломанные теги, брейсы и строковые литералы. Нужен второй гейт.
- Русский сайт — это шаг 1 программы (строки), контент `docs-lab`, сборка сайта с русской i18n и хостинг — отдельные изменения. Гейт этого шага не должен тянуть полную сборку Next.js.

## Цели / нецели

**Цели:**

- Ревью перевода отдельным инструментом, применимым к свежему переводу сразу после валидации.
- Advisor-модель настраивается независимо от переводящей (может быть сильнее и дороже).
- Статус `reviewed` ставится только после детерминированно разобранного pass-вердикта.
- Каждый переведённый сайтовый файл проходит синтаксический гейт TypeScript.

**Нецели:**

- Автоматические правки по замечаниям ревью — доработка остаётся человеку (или следующему запуску перевода в delta).
- Полная сборка сайта (`sync:docs`, `next build`), i18n-инфраструктура, русский поиск/slugify/шрифты — изменение «русский сайт» (шаг 3 программы).
- Перевод контента `docs-lab`, ревью-прогон существующих machine-файлов — отдельные изменения.
- Батч-UI, веб-интерфейс ревью — только CLI.

## Решения

### D1: Ревью — отдельный инструмент `tools/review-translation.mjs`

Свой инструмент, а не этап внутри `translate.mjs`:

- Точка входа «только ревью» нужна и после свежего перевода, и для повторного прогона отдельного файла без перевода.
- `translate.mjs` после успешной валидации вызывает тот же модуль ревью, не дублируя логику.

Использование: `node tools/review-translation.mjs <en-путь | ru-путь>`. Ревью отказывается работать, если drift-check фиксирует расхождение `base_blob_sha` записи с апстримом — иначе ревью устаревшей пары могло бы «подтвердить» отставание (advisor, finding 10).

**Альтернатива** — встроить ревью в `translate.mjs` флагом: отвергнута, раздваивает вызовы и мешает повторному прогону.

### D2: Конфигурация advisor — отдельный префикс env

`REVIEW_API_BASE`, `REVIEW_API_KEY`, `REVIEW_API_MODEL`, `REVIEW_API_FLAVOR` (`openai` | `anthropic`), опционально `REVIEW_API_MAX_TOKENS`. Тот же HTTP-паттерн без SDK-локина, что и у `TRANSLATE_API_*`. Симметрия конфигураций позволяет держать переводящую модель дешёвой, а advisor — сильной. Пустой конфиг advisor не блокирует перевод: файл остаётся `machine`, ревью откладывается (спека «Независимая конфигурация advisor-модели»).

**Альтернатива** — переиспользовать `TRANSLATE_API_*`: отвергнута, жёстко связывает две роли с разными требованиями к качеству.

### D3: Протокол ответа advisor — строгий JSON, детерминированный разбор

Промпт ревью: системная роль (ревьюер перевода EN→RU по глоссарию и стайлгайду) + `glossary.md` + `style-guide.md` + EN-файл + RU-файл. Ответ — один JSON-блок:

```json
{ "verdict": "pass" | "fail",
  "issues": [ { "fragment_en": "...", "fragment_ru": "...", "problem": "..." } ] }
```

Разбор: извлечение JSON-блока, проверка схемы (verdict ∈ {pass, fail}, fail требует непустой issues). Непарсимый ответ → ретрай (до 3 попыток), затем команда падает без смены статуса. Температура 0 там, где модель её принимает. Только разобранный `pass` приводит к `mark-translated <path> reviewed`; `fail` печатает перечень замечаний и проблемные фрагменты.

Ограничение честности (advisor, finding 8): pass-вердикт LLM не доказывает читабельность. `reviewed` — верх машинной шкалы, а не гарантия качества; финальная редакторская приёмка — человек, выборочная, в рамках отдельного изменения контента.

### D4: Статусная дисциплина

- `machine` проставляет только `translate.mjs` после валидации (без изменений).
- `reviewed` проставляет только `review-translation.mjs` после pass-вердикта и только если drift-check чист. Человек сохраняет право вручную понизить статус через `mark-translated <path> machine` — финальный авторитет не отзывается.

### D5: Один проход — 17 файлов зоны `website`

Ранее планировалась вторая волна (ревью-прогон 26 machine-файлов) — вынесена из этого изменения (advisor, finding 13: смешение несвязанной работы раздувает change). Здесь: перевод каждого из 17 файлов, ревью сразу после каждого. Терминологические проблемы, всплывшие на первых файлах, правят глоссарий до перевода остальных.

### D6: Синтаксический гейт сайтовых файлов — `tools/gate-website-ru.mjs`

Regex-валидатор не парсит JSX. Гейт: каждый RU-файл зоны `website` прогоняется через `ts.transpileModule` (TypeScript compiler API, режим JSX, `reportDiagnostics`). Любая syntax-ошибка = отказ, манифест не обновляется до reviewed. Запуск: после перевода и до ревью (входной фильтр) и как самостоятельная команда CI (`node tools/gate-website-ru.mjs`, проверяет все RU-файлы зоны `website`).

**Альтернатива** — полный `pnpm install && next build` как гейт: правильна для шага 3 (сборка сайта), но тяжела для шага 1 — тянет зависимости сайта и контент docs-lab, который ещё английский. `tsc --noEmit` без установленных зависимостей сайта даёт шум «cannot find module». `transpileModule` ловит реалистичный класс поломок LLM (брейсы, теги, кавычки) без инфраструктуры сайта.

## Риски / компромиссы

- [Advisor пропускает терминологическую ошибку] → глоссарий-линт остаётся обязательным и детерминированным; advisor работает поверх него, а не вместо. Человек может понизить статус.
- [LLM ревьюит LLM той же семьи — систематические кальки] → переводящая и advisor-модели настраиваются независимо (D2); рекомендуется разная семья. Статус `reviewed` не называется гарантией читабельности (D3).
- [Regex-валидатор пропускает JSX-поломку] → гейт D6 обязателен до `reviewed`.
- [Непарсимые ответы advisor съедают ретраи] → лимит 3 попытки; файл остаётся `machine` без побочных эффектов, повторный прогон дешёв.
- [OAuth-токен pi как credential раннера] → токен рефрешится на каждый запуск (`tools/kimi-token.mjs`), ротации refresh-токена нет (проверено 2026-10-31); риск по ToS принят временно, выход — официальный API-ключ Moonshot. При 401 раннер падает с понятной ошибкой, манифест не портится.
- [Разногласие с архивным дизайном translation-pipeline («reviewed только человек»)] → осознанная смена решения, зафиксированная в proposal.md; сценарии дельта-спецификации определяют новый контракт.

## Открытые вопросы

- Конкретная модель advisor не фиксируется — выбирается через `REVIEW_API_MODEL` при прогоне. Для независимости рекомендуется семья, отличная от переводящей.
- Архитектура сайта (standalone-RU vs двуязычный `/ru` с hreflang) — решается в изменении «русский сайт» (шаг 3), здесь не блокирует.
