# Дизайн: openspec-ru-ui

## Контекст

См. `proposal.md` — мотивация и список изменений. Дизайн веб-интерфейса уже подготовлен в файле `C:\Users\egor\Downloads\openspec-ru-ui.html` (самодостаточный шаблон на базе CSS-переменных для светлой/тёмной темы, Tailwind CDN, Alpine.js 3.14 и встроенного парсера Markdown/спецификаций/задач). В репозитории уже есть CLI `tools/apply/cli.mjs` (`bin: openspec-ru`), через который пользователи запускают `npx github:OnePro/openspec_ru ...`.

## Цели и не-цели

**Цели:**

- Запуск веб-панели одной командой `openspec-ru start web [--port <port>] [--no-open]` и остановка через `openspec-ru stop web`, кнопку в UI или `Ctrl+C`.
- Мгновенная блокировка с кодом `1`, если в целевой папке нет каталога `openspec/`.
- Перенос эталонного дизайна из `openspec-ru-ui.html` один-в-один с подключением к реальным файлам `openspec/changes/**` и `openspec/specs/**` через JSON API и SSE.
- Кроссплатформенность (нормализация путей `/` на Windows/Linux/macOS, корректная UTF-8 кириллица) и 0 внешних npm-зависимостей на сервере.

**Не-цели:**

- Редактирование/создание спецификаций или идей из браузера (строго read-only).
- Мульти-репозиторный конфигурационный файл — сервер всегда работает от каталога `openspec/` текущего репозитория.

## Решения

### D1: Архитектура сервера без зависимостей (`node:http` + `node:fs`)

Сервер реализуется в `tools/web/server.mjs` на встроенных модулях Node.js (`http`, `fs`, `path`):

- `GET /` — отдаёт HTML веб-панели (`tools/web/ui.html`, адаптированный из `openspec-ru-ui.html`);
- `GET /api/state` — сканирует `openspec/specs/**` и `openspec/changes/**` (включая `openspec/changes/archive/**`) и возвращает единый JSON-снимок `{ repoName, bundleVersion, changes, specs }`, где у каждого изменения и спецификации уже переданы сырые Markdown-тексты файлов (`proposal`, `design`, `tasks`, `specFiles`), чтобы клиентские функции `buildChange` и `buildSpec` из дизайн-макета работали без искажений;
- `GET /api/events` — поток Server-Sent Events (`text/event-stream`), отправляющий `event: update` при срабатывании `fs.watch(openspecDir, { recursive: true })` с дебаунсом `250ms`;
- `POST /api/shutdown` — аккуратное завершение работы сервера по клику на кнопку выключения в шапке UI.

**Почему `GET /api/state` одним снимком, а не десятки мелких запросов**: все Markdown-файлы `openspec/` одного репозитория занимают десятки килобайт; отдача полного снимка за один запрос избавляет от проблем с URL-кодированием кириллицы и вложенных слэшей в роутах (из-за которых ломался `ToruAI/openspec-ui`) и позволяет клиентскому поиску мгновенно искать по тексту всех документов.

### D2: Жизненный цикл процесса и файл состояния для `stop web`

При старте `openspec-ru start web`:
1. Проверяется наличие `<projectDir>/openspec` (иначе выход с кодом `1`).
2. Если `--port` задан явно — сервер пытается занять именно его; если не задан — пробует `3000`, а при `EADDRINUSE` перебирает `3001..3010`.
3. После успешного `listen` записывается файл состояния (в `.git/openspec-ru-web.json`, либо в `os.tmpdir()` по хешу пути проекта, если `.git` — файл): `{ pid, port, projectDir, startedAt }`.
4. Команда `openspec-ru stop web` читает этот файл, отправляет `POST http://127.0.0.1:<port>/api/shutdown` (с фолбэком на `process.kill(pid, 'SIGTERM')`) и удаляет файл состояния. При `SIGINT`/`SIGTERM`/выходе файл состояния также очищается.
5. При флаге `--detach` (`-d`) CLI порождает отвязанный фоновый процесс (`detached: true`, `stdio: 'ignore'`, `unref()`), ждёт появления и живости сервера по state-файлу (до 3 с), выводит URL и завершается с кодом `0`, не блокируя bash-инструмент AI-агента. Если сервер для этого репозитория уже запущен и отвечает на `/api/state`, повторный `start web --detach` переиспользует запущенный экземпляр.
6. Скилл `openspec-ui` и команда `ui` генерируются в `dist-ru/` (`tools/build-ru.mjs` + статический генератор) и устанавливаются `applyRuPatch` во все обнаруженные инструменты проекта.

### D3: Интеграция дизайн-макета `openspec-ru-ui.html`

Макет дизайнера (`openspec-ru-ui.html`) переносится в `tools/web/ui.html` с сохранением всех CSS-переменных, классов, иконок и функций рендера (`md()`, `parseSpec()`, `renderSpecBody()`, `parseTasks()`, `renderTasks()`, `buildChange()`, `buildSpec()`). Изменения только в слое данных:
- вместо захардкоженных `<script type="text/markdown">` и констант `CHANGES`/`SPECS` состояние загружается через `fetch('/api/state')` при инициализации Alpine-компонента `app()` и при получении SSE-события `update` из `new EventSource('/api/events')`;
- индикатор `Live / Отключено` привязывается к реальному состоянию `EventSource` (`onopen` / `onerror`);
- в шапку рядом с переключателем темы добавляется кнопка выключения сервера (`POST /api/shutdown`).

## Риски и компромиссы

- [`fs.watch({ recursive: true })` может генерировать дублирующиеся события на Windows/macOS] → дебаунс 250 мс перед отправкой SSE-события `update`.
- [CDN Tailwind/Alpine при полном отсутствии интернета] → для локальной разработки с AI-агентами интернет всегда активен; HTML остаётся одним компактным файлом без шага сборки фронтенда.
- [Зомби-файл состояния после `kill -9`] → `stop web` и повторный `start web` проверяют живость процесса (`GET /api/state` / `process.kill(pid, 0)`) и очищают устаревший файл состояния.
