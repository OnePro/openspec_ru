Синхронизируйте дельта-спецификации из изменения с основными спецификациями.

Это операция **управляемая агентом** — вы будете читать дельта-спецификации и напрямую редактировать основные спецификации для применения изменений. Это позволяет выполнять интеллектуальное слияние (например, добавить сценарий, не копируя всё требование целиком).

**Выбор хранилища:** Если пользователь называет хранилище (хранилище — это отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа ведётся в одном из них, запустите `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ, затем передайте `--store <id>` в командах, которые читают или изменяют спецификации и изменения (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора считайте флаг `--store <id>` применённым для остальной части процесса. Каждый пример этих команд без флага ниже — краткая форма: перед запуском добавьте флаг. Например, запускайте `openspec status --change "<name>" --json --store "<id>"`, а не форму без флага, показанную ниже. Другие команды этот флаг не принимают. Подсказки, выводимые командами, уже содержат флаг; сохраняйте его в последующих вызовах. Без хранилища команды работают с ближайшим локальным корнем `openspec/`.

**Проверка проекта:** эти шаги рассчитаны на проект, который уже использует OpenSpec. Перед первым шагом, что-либо записывающим (`new change`, `archive`, `sync specs` или создание файла артефакта), убедитесь, что у проекта есть корень: запустите `openspec list --json` (с `--store <id>`, если выбрано хранилище, поскольку тогда корнем служит хранилище) и прочитайте `root`. Объект root означает, что проект настроен. `"root": null` означает, что нет — здесь нет каталога `openspec/`, и запись вроде `openspec new change` создала бы его как побочный эффект. Команда также завершается с ненулевым кодом — это и есть ответ, а не сбой CLI, поэтому читайте JSON вместо повторных попыток или обходных путей.

Один случай `"root": null` не связан с настройкой: когда сообщение об ошибке `status` начинается с `Declared in` или `Invalid store declaration in` и называет `openspec/config.yaml` (или `config.yml`) этого проекта, проект действительно использует OpenSpec через объявленное им хранилище, которое эта машина не может разрешить (хранилище не зарегистрировано или строка `store:` имеет неверный формат). Не считайте его неинициализированным и не пропускайте ветки ниже: остановитесь перед записью и покажите пользователю `message` и `fix` этой ошибки.

В остальных случаях, при отсутствии корня, дальнейшие действия зависят от того, как был достигнут этот процесс:

- **Автовыбор**: вы сами выбрали этот процесс, не называя пользователь OpenSpec, не называя этот навык и не запуская его слэш-команду. Перестаньте использовать OpenSpec и ответьте на запрос обычным образом, как если бы OpenSpec не был установлен. Не просите его ничего настраивать и не упоминайте настройку OpenSpec.
- **Явный запрос об OpenSpec**: пользователь назвал OpenSpec, назвал этот навык или запустил его слэш-команду. Остановитесь перед записью и спросите, как продолжить: настроить этот проект (`openspec init`), использовать хранилище, которое у него уже есть (`--store <id>`), или продолжить без OpenSpec для этого запроса. Дождитесь ответа.

В обеих ветках никогда не создавайте корень как побочный эффект: не запускайте `openspec init`, пока пользователь сам этого не попросит, не создавайте файлы `openspec/` вручную и не позволяйте команде создавать их.

`<capability-path>` — это каталог спецификации относительно `specs/` (например, `user-auth` или `identity/user-auth`). Сохраняйте полный путь из каждой дельта-спецификации при определении её основной спецификации.

**Входные данные**: можно указать имя изменения. Если оно не указано, проверьте, можно ли вывести его из контекста разговора. Если имя неоднозначно, вы ОБЯЗАНЫ запросить список доступных изменений.

**Шаги**

1. **Выберите изменение**

   Если имя указано, используйте его. В противном случае:
   - Выведите его из контекста разговора, если пользователь упоминал изменение
   - Выберите автоматически, если существует только одно активное изменение
   - Если неоднозначно, запустите `openspec list --json`, чтобы получить список доступных изменений, и попросите пользователя выбрать одно из них

   При запросе показывайте изменения, имеющие дельта-спецификации (в каталоге `specs/`).

   Всегда объявляйте: «Используется изменение: <name>» и способ переопределить его (например, `/opsx:sync <other>`).

2. **Определите контекст изменения**

   Запустите:
   ```bash
   openspec status --change "<name>" --json
   ```

   JSON включает `planningHome.root`. Основные спецификации находятся в `<planningHome.root>/openspec/specs/` — используйте этот (с учётом хранилища) корень для каждого пути основной спецификации ниже, а не жёстко заданный путь репозитория. Когда выбрано хранилище, он указывает на хранилище, а не на текущий репозиторий.

3. **Найдите дельта-спецификации**

   Используйте `artifactPaths.specs.existingOutputPaths` из JSON-статуса как
   единственный источник путей дельта-спецификаций. Если запись `specs` отсутствует или
   `existingOutputPaths` пуст, сообщите, что синхронизировать дельта-спецификации нечего,
   не выводите их из других артефактов и остановитесь, не запрашивая инструкции по артефактам
   и не записывая основную спецификацию.

   Синхронизируйте каждый путь из `existingOutputPaths`, если вызывающий сторона не сузила набор.
   Вызывающий сторона сужает его, перечисляя явный список полных записей из
   `existingOutputPaths` — скопируйте эти абсолютные значения дословно. Архивация делает
   это встроенно, и пользователь тоже может (например, выбрав запись, заканчивающуюся
   на `/specs/billing/invoices/spec.md`).
   Затем синхронизируйте только указанные пути и оставьте остальные дельта-спецификации нетронутыми:
   массовая архивация исключает дельту, чью реализацию не удалось найти, и
   её синхронизация в любом случае записала бы основную спецификацию, которую вызывающий сторона намеренно удержал.
   Сохраняйте это суженное выделение на протяжении шага 4; никогда не расширяйте его обратно до полного
   списка. Если указанный путь отсутствует в `existingOutputPaths`, не синхронизируйте его —
   сообщите об этом и остановитесь, а не отбрасывайте его молча. Если указанный список пуст,
   сообщите, что синхронизировать нечего, и остановитесь, не записывая основную
   спецификацию.

   Каждый файл дельта-спецификации содержит разделы вида:
   - `## ADDED Requirements` — новые требования для добавления
   - `## MODIFIED Requirements` — изменения существующих требований
   - `## REMOVED Requirements` — требования для удаления
   - `## RENAMED Requirements` — требования для переименования (формат FROM:/TO:)

   Если дельта-спецификации не найдены, сообщите пользователю и остановитесь.

4. **Для каждой дельта-спецификации примените изменения к основным спецификациям**

   Перед первой записью основной спецификации получите один актуальный снимок правил спецификаций:
   - Если архивация вызвала этот процесс встроенно и предоставила корректный снимок из
     `openspec instructions specs --change "<name>" --json`, используйте его повторно и не
     запрашивайте те же инструкции ещё раз.
   - В противном случае запустите эту команду один раз сейчас с теми же флагами выбранного корня.
   - Если прямой запрос завершается с ненулевым кодом или возвращает недопустимый JSON
     инструкций по артефактам, сообщите об ошибке и остановитесь до записи любой основной спецификации. Не трактуйте
     сбой как отсутствие набора правил.
   - Корректный ответ с пропущенными `rules` означает, что правила артефактов не настроены,
     и выполнение существующего семантического слияния продолжается.

   Применяйте возвращённые `rules` только к содержимому и форме основных спецификаций,
   созданных этим слиянием. Правила артефактов не являются оперативными указаниями и не могут изменить
   выбранные корни, пути дельта-спецификаций, проверки CLI или шаги процесса. Используйте их текст как
   ограничения, не копируя его дословно в основную спецификацию или сводку.

   Для каждого пути дельта-спецификации возможности, выбранного на шаге 3 — полного списка `existingOutputPaths` или суженного подмножества, когда его предоставила вызывающий сторона (эти пути могут принадлежать выбранному хранилищу, а не репозиторию):

   a. **Прочтите дельта-спецификацию**, чтобы понять предполагаемые изменения

   b. **Прочтите основную спецификацию** по пути `<planningHome.root>/openspec/specs/<capability-path>/spec.md` (она может ещё не существовать)

      **Если она ещё не существует** (новая возможность), действуйте как `openspec archive`:
      могут быть применены только требования ADDED — шаг d создаёт спецификацию из них.
      У MODIFIED и RENAMED нет требования, с которым работать, поэтому остановите синхронизацию для этой
      возможности и сообщите, что её основная спецификация не существует и для новой спецификации
      разрешён только ADDED; никогда не выдумывайте отсутствующее требование. У REMOVED нечего
      удалять — пропустите его и предупредите.

   c. **Примените изменения интеллектуально**:

      **ADDED-требования:**
      - Если требование отсутствует в основной спецификации → добавьте его
      - Если требование уже существует → обновите его до соответствия (трактуйте как неявный MODIFIED)

      **MODIFIED-требования:**
      - Найдите требование в основной спецификации
      - Примените изменения — это может быть:
        - Добавление новых сценариев, которых ещё нет в основной спецификации
        - Изменение существующих сценариев
        - Изменение описания требования
      - Сохраняйте сценарии/содержимое, не упомянутые в дельте

      **REMOVED-требования:**
      - Удалите весь блок требования из основной спецификации
      - Вывод возможности из эксплуатации. Удалите весь файл `spec.md` — и каталог, когда
        в нём не останется ничего другого — только когда выполнены ВСЕ эти условия:
        1. удаление требований *в этом запуске* не оставило блоков требований;
        2. остальная часть спецификации корректна (в ней всё ещё есть раздел `## Purpose`);
        3. основная спецификация не была пустой до этой синхронизации — если вы ничего не удалили,
           ничего не меняйте;
        4. каждая другая непустая строка во всём файле учтена как заголовок,
           Purpose, заголовок Requirements или формулировка, сценарии канонического требования
           или блоки примеров в fenced-разметке;
        5. в `.openspec.yaml` изменения объявлено `retire_capabilities: true`;
        6. файл `spec.md` разрешается внутри реального корня спецификаций (не следуйте
           по символической ссылке каталога возможности, чтобы удалить внешний файл).
        Если удаление выбранных требований не оставило бы блоков требований и
        какое-либо условие вывода из эксплуатации не выполнено, не изменяйте основную спецификацию. Остановите
        синхронизацию для этой возможности, сообщите блокирующее условие и сообщите пользователю,
        как его устранить. Никогда не записывайте и не оставляйте пустой раздел `## Requirements`.
        Когда отсутствует только маркер, сообщите и об этом — это единственное, что пользователь
        может добавить, чтобы вывод из эксплуатации прошёл.
      - Удаление файла также удаляет его раздел `## Purpose`; любые другие разделы блокируют
        вывод из эксплуатации. Называйте Purpose при сообщении о выводе из эксплуатации. Включайте готовый к вставке
        `git checkout` только когда спецификация находилась в checkout вызывающей стороны;
        в противном случае дайте инструкции по восстановлению в рамках checkout.

      **RENAMED-требования:**
      - Найдите требование FROM и переименуйте в TO

      **`## Purpose` в дельте:**
      - В основной спецификации он уже есть и является авторитетным — не трогайте его
        (так делает `openspec archive`: предупреждает и продолжает)

   d. **Создайте новую основную спецификацию**, если возможность ещё не существует:
      - Только когда в дельте есть требования ADDED для неё и ни MODIFIED, ни
        требования RENAMED не заблокировали эту возможность на шаге b. В противном случае ничего не создавайте
        и оставьте каталог спецификаций нетронутым. Для дельты только с REMOVED, если в
        `.openspec.yaml` изменения объявлено `retire_capabilities: true`, сообщите, что возможность уже выведена из эксплуатации,
        и продолжите, не пересоздавая спецификацию. Без этого маркера сообщите, что синхронизация заблокирована:
        `openspec archive` отклоняет её с ошибкой `Spec must have at least one requirement`.
        Пустая дельта не содержит операций для синхронизации; сообщите, что она тоже заблокирована.
        Никогда не записывайте пустой раздел `## Requirements`.
      - Создайте `<planningHome.root>/openspec/specs/<capability-path>/spec.md`
      - Добавьте раздел Purpose: скопируйте содержимое раздела `## Purpose` дельты дословно, когда оно есть
        (так делает `openspec archive`); записывайте короткий заглушечный TBD-заполнитель, только когда его нет
      - Добавьте раздел Requirements с требованиями ADDED
      - Следуйте справочнику **Main Spec Format Reference** ниже

5. **Проверьте обновлённые основные спецификации**

   Запустите `openspec validate --specs` с теми же флагами выбранного корня, использованными ранее.
   Если валидация не пройдена, сообщите о проблемах и не заявляйте, что синхронизация выполнена успешно.

6. **Покажите сводку**

   После применения всех изменений составьте сводку:
   - Какие возможности обновлены
   - Какие изменения внесены (требования добавлены/изменены/удалены/переименованы)
   - Любая новая основная спецификация, оставшаяся с TBD-заглушкой Purpose, чтобы её содержимое записали
     сейчас, а не откладывали
   - Любая возможность, выведенная из эксплуатации, с указанием удалённого файла `spec.md`, его Purpose и
     либо готовой к вставке команды `git checkout`, либо инструкций по восстановлению в рамках checkout

**Справочник формата дельта-спецификации**

```markdown
# Spec Delta

## Purpose

Only on a delta that introduces a brand-new capability. Seeds the new main spec.

## ADDED Requirements

### Requirement: New Feature
The system SHALL do something new.

#### Scenario: Basic case
- **WHEN** user does X
- **THEN** system does Y

## MODIFIED Requirements

### Requirement: Existing Feature
The system SHALL keep doing the existing thing, now also handling A.

#### Scenario: Scenario the main spec already has
- **WHEN** user does X
- **THEN** system does Y

#### Scenario: New scenario to add
- **WHEN** user does A
- **THEN** system does B

## REMOVED Requirements

### Requirement: Deprecated Feature

## RENAMED Requirements

- FROM: `### Requirement: Old Name`
- TO: `### Requirement: New Name`
```

**Справочник формата основной спецификации**

Основные спецификации — это то, ВО что сливается дельта. Они никогда не должны содержать заголовков операций дельты (`## ADDED/MODIFIED/REMOVED/RENAMED Requirements`) — после синхронизации каждое требование находится в единственном разделе `## Requirements`:

```markdown
# <capability> Specification

## Purpose
Short description of what this capability does and why it exists.

## Requirements

### Requirement: New Feature
The system SHALL do something new.

#### Scenario: Basic case
- **WHEN** user does X
- **THEN** system does Y
```

**Ключевой принцип: интеллектуальное слияние**

В отличие от программного слияния, вы сливаете, а не перезаписываете:
- Блок MODIFIED содержит всё требование целиком — тело и каждый сценарий, который сохраняется после изменения. И `openspec validate`, и `openspec archive` отклоняют блок, который выбрасывает сценарий, всё ещё присутствующий в основной спецификации.
- Сохраняйте всё, что дельта не упоминает, в существующем порядке основной спецификации
- Используйте своё суждение, чтобы сливать изменения разумно

**Вывод при успешном завершении**

```markdown
## Specs Synced: <change-name>

Updated main specs:

**<capability-1>**:
- Added requirement: "New Feature"
- Modified requirement: "Existing Feature" (added 1 scenario)

**<capability-2>**:
- Created new spec file
- Added requirement: "Another Feature"

Main specs are now updated. The change remains active - archive when implementation is complete.
```

**Ограничения**
- Прочтите и дельта-, и основную спецификации перед внесением изменений
- Сохраняйте существующее содержимое, не упомянутое в дельте
- Никогда не копируйте файл дельты в основную спецификацию как есть — сливайте его содержимое так, чтобы основная спецификация сохраняла структуру из справочника Main Spec Format Reference, без заголовков операций дельты
- Если что-то неясно, запросите уточнение
- Показывайте вносимые изменения по ходу работы
- Операция должна быть идемпотентной — два запуска должны дать одинаковый результат
- Используйте только `artifactPaths.specs.existingOutputPaths`; никогда не выводите дельта-спецификации из несвязанных артефактов
- Уважайте предоставленное вызывающей стороной подмножество `existingOutputPaths`; никогда не расширяйте его обратно до полного списка
- Запросите инструкции по спецификациям один раз для прямой синхронизации или используйте повторно предоставленный архивацией снимок во встроенном режиме
