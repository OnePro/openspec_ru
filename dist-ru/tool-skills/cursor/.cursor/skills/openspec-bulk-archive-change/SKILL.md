Архивирует несколько завершённых изменений в одной операции.

Этот навык позволяет выполнять пакетное архивирование изменений, разрешая конфликты спецификаций интеллектуально — с проверкой кодовой базы, чтобы определить, что реально реализовано.

**Выбор хранилища:** Если пользователь называет хранилище (хранилище — это отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа ведётся в одном из них, запустите `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ, затем передайте `--store <id>` в командах, которые читают или изменяют спецификации и изменения (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора считайте флаг `--store <id>` применённым для остальной части процесса. Каждый пример этих команд без флага ниже — краткая форма: перед запуском добавьте флаг. Например, запускайте `openspec status --change "<name>" --json --store "<id>"`, а не форму без флага, показанную ниже. Другие команды этот флаг не принимают. Подсказки, выводимые командами, уже содержат флаг; сохраняйте его в последующих вызовах. Без хранилища команды работают с ближайшим локальным корнем `openspec/`.

**Проверка проекта:** эти шаги рассчитаны на проект, который уже использует OpenSpec. Перед первым шагом, что-либо записывающим (`new change`, `archive`, `sync specs` или создание файла артефакта), убедитесь, что у проекта есть корень: запустите `openspec list --json` (с `--store <id>`, если выбрано хранилище, поскольку тогда корнем служит хранилище) и прочитайте `root`. Объект root означает, что проект настроен. `"root": null` означает, что нет — здесь нет каталога `openspec/`, и запись вроде `openspec new change` создала бы его как побочный эффект. Команда также завершается с ненулевым кодом — это и есть ответ, а не сбой CLI, поэтому читайте JSON вместо повторных попыток или обходных путей.

Один случай `"root": null` не связан с настройкой: когда сообщение об ошибке `status` начинается с `Declared in` или `Invalid store declaration in` и называет `openspec/config.yaml` (или `config.yml`) этого проекта, проект действительно использует OpenSpec через объявленное им хранилище, которое эта машина не может разрешить (хранилище не зарегистрировано или строка `store:` имеет неверный формат). Не считайте его неинициализированным и не пропускайте ветки ниже: остановитесь перед записью и покажите пользователю `message` и `fix` этой ошибки.

В остальных случаях, при отсутствии корня, дальнейшие действия зависят от того, как был достигнут этот процесс:

- **Автовыбор**: вы сами выбрали этот процесс, не называя пользователь OpenSpec, не называя этот навык и не запуская его слэш-команду. Перестаньте использовать OpenSpec и ответьте на запрос обычным образом, как если бы OpenSpec не был установлен. Не просите его ничего настраивать и не упоминайте настройку OpenSpec.
- **Явный запрос об OpenSpec**: пользователь назвал OpenSpec, назвал этот навык или запустил его слэш-команду. Остановитесь перед записью и спросите, как продолжить: настроить этот проект (`openspec init`), использовать хранилище, которое у него уже есть (`--store <id>`), или продолжить без OpenSpec для этого запроса. Дождитесь ответа.

В обеих ветках никогда не создавайте корень как побочный эффект: не запускайте `openspec init`, пока пользователь сам этого не попросит, не создавайте файлы `openspec/` вручную и не позволяйте команде создавать их.

`<capability-path>` — это каталог спецификации относительно `specs/` (например, `user-auth` или `identity/user-auth`). Сохраняйте полный путь из каждой дельта-спецификации при определении её основной спецификации.

**Входные данные**: не требуются (запрашивает выбор)

**Шаги**

1. **Получите активные изменения**

   Запустите `openspec list --json`, чтобы получить все активные изменения.

   Если активных изменений нет, сообщите об этом пользователю и остановитесь.

2. **Запросите выбор изменений**

   Попросите пользователя выбрать изменения (множественный выбор):
   - Покажите имя каждого изменения и статус задач из вывода списка
   - Включите вариант «Все изменения»
   - Разрешите любое количество выбранных (1+ допустимо, 2+ — типичный случай)

   **ВАЖНО**: НЕ выбирайте автоматически. Всегда предоставляйте выбор пользователю.

   **Загрузите текущие входные данные архивирования один раз для выбранного корня перед пакетной валидацией:**

   Выберите одно изменение из этого корня и запустите
   `openspec instructions archive --change "<selected-change>" --json` с теми же
   флагами выбранного корня. Этот запрос носит рекомендательный и необязательный характер:
   он лишь предоставляет дополнительные входные данные для подсказки, поэтому никогда
   не должен блокировать пакет. Если он завершается ошибкой или возвращает
   недопустимый JSON — например, в старой версии CLI, которая ещё не поддерживает
   эту команду, — продолжите пакет без контекста и без указаний по операции. Не
   сообщайте об ошибке и не останавливайтесь.

   Допустимый ответ может не содержать `context` и `operationGuidance`. Считайте
   `context` обязательным входным данным уровня подсказки для всего пакета: прочитайте
   и учтите его, примените соответствующие факты проекта, соглашения и ограничения.
   Считайте `operationGuidance` необязательным дополнительным советом: прочитайте и
   учтите каждую запись и следуйте тем, что применимы и совместимы со встроенным
   пакетным процессом.

   Держите оба поля отдельно от анализа конфликтов, явных выборов пользователя,
   разрешённых путей, проверок CLI и контрактов команд. Если контекст конфликтует с одним
   из этих управляющих входных данных, сообщите о конфликте и сохраните управляющее
   значение. Если указание неприменимо или конфликтует с управляющим входным данным, не
   следуйте ему и объясните, почему. Не выводите пропущенные подсказки, пути замены
   или флаги из этих полей и не копируйте их текст дословно в спецификации, изменения
   или сводки. Это контракты поведения уровня подсказки, а не принудительные проверки.

3. **Пакетная валидация — сбор статуса для всех выбранных изменений**

   Запустите `openspec list --json` один раз с теми же флагами выбранного корня для
   прогресса задач. Если запрос завершается ошибкой, возвращает недопустимый JSON, не
   содержит какое-либо выбранное изменение, содержит дубликат выбранного изменения
   или возвращает недопустимые счётчики, сообщите о проблеме и остановитесь до
   синхронизации или архивирования пакета.

   Для каждого выбранного изменения соберите:

   a. **Статус артефактов** — запустите `openspec status --change "<name>" --json`
      - Разберите `schemaName`, `artifacts`, `planningHome`, `changeRoot`, `artifactPaths` и `actionContext`
      - Отметьте, какие артефакты имеют состояние `done`, а какие — иное

   b. **Завершение задач** — найдите запись `changes` в ответе списка, чьё `name` в точности совпадает с этим изменением
      - Требуйте неотрицательные целые `totalTasks` и `completedTasks`, причём `completedTasks <= totalTasks`
      - Незавершённые задачи = `totalTasks - completedTasks`
      - CLI определяет отслеживаемые схемой файлы задач, включая пользовательские имена артефактов, выходные пути и глобы
      - Не выводите завершение задач из статуса артефактов, идентификатора артефакта `tasks` или отсутствия корневого `tasks.md`
      - CLI считает завершёнными только маркеры чекбоксов `x`/`X`; другие маркеры остаются незавершёнными
      - Если `totalTasks` равен нулю, отметьте как «Нет задач»

   c. **Дельта-спецификации** — проверьте `artifactPaths.specs.existingOutputPaths` из JSON статуса
      - Перечислите, какие спецификации возможностей существуют
      - Для каждой извлеките имена требований (строки, соответствующие `### Requirement: <name>`)
      - Считайте этот список единственным источником дельта-спецификаций. Если запись `specs`
        отсутствует или список пуст, не выполняйте синхронизацию спецификаций и запрос
        инструкций specs для этого изменения; не выводите дельты из несвязанных артефактов.
      - Оценивайте это независимо для каждого изменения, включая пакеты со смешанными схемами,
        где у некоторых схем нет артефакта `specs`.

   d. **Цель архивирования** — вычислите целевое имя каждого изменения один раз и запишите его как `<target-name>` этого изменения
      - Используйте имя изменения как есть, если оно уже начинается с префикса `YYYY-MM-DD-`; в противном случае добавьте текущую дату как `YYYY-MM-DD-<name>` (то же правило, что у `openspec archive`)
      - Проверьте, существует ли уже `<planningHome.changesDir>/archive/<target-name>`
      - Если он существует или другое выбранное изменение разрешается в то же целевое имя, отметьте каждое такое изменение как `Blocked` с причиной `Archive directory already exists`
      - Заблокированное изменение никогда не синхронизируется и не перемещается: покажите его как `Blocked` в таблице шага 6, исключите из разрешения конфликтов (разрешайте его конфликты, используя только другие изменения) и запишите как Failed в шаге 8d
      - Проверка здесь, до записи любой основной спецификации, соответствует `openspec archive`: коллизия, найденная после синхронизации, оставила бы основные спецификации перезаписанными ради архива, который не состоялся

4. **Обнаружение конфликтов спецификаций**

   Постройте карту с ключом `<capability-path>` — точным путём относительно `specs/`:

   ```text
   identity/user-auth -> [change-a, change-b]  <- CONFLICT (2+ изменения)
   billing/user-auth  -> [change-c]            <- OK (другой полный путь)
   ```

   Конфликт существует, когда 2+ выбранных изменений имеют дельта-спецификации для одного и того же точного `<capability-path>`.

5. **Разрешение конфликтов агентно**

   **Для каждого конфликта** исследуйте кодовую базу:

   a. **Прочитайте дельта-спецификации** из каждого конфликтующего изменения, чтобы понять, что каждое из них заявляет добавить/изменить

   b. **Найдите в кодовой базе** свидетельства реализации:
      - Ищите код, реализующий требования из каждой дельта-спецификации
      - Проверьте связанные файлы, функции или тесты

   c. **Определите разрешение**:
      - Если реально реализовано только одно изменение -> синхронизируйте спецификации только его
      - Если реализованы оба -> примените в хронологическом порядке (сначала старшее, новее перезаписывает)
      - Если не реализовано ни одно -> пропустите синхронизацию спецификаций, предупредите пользователя

   d. **Запишите разрешение** для каждого конфликта:
      - Решение о включении или исключении для каждой дельта-спецификации, с ключом по изменению и `<capability-path>`
      - Какие включённые дельта-спецификации применить и в каком порядке
      - Какие дельта-спецификации исключить из синхронизации, потому что их реализация отсутствует
      - Обоснование (что найдено в кодовой базе)

6. **Покажите сводную таблицу статусов**

   Покажите таблицу, суммирующую все изменения:

   ```markdown
   | Change              | Artifacts | Tasks | Specs   | Conflicts | Status |
   |---------------------|-----------|-------|---------|-----------|--------|
   | schema-management   | Done      | 5/5   | 2 delta | None      | Ready  |
   | project-config      | Done      | 3/3   | 1 delta | None      | Ready  |
   | add-oauth           | Done      | 4/4   | 1 delta | identity/user-auth (!) | Ready* |
   | add-verify-skill    | 1 left    | 2/5   | None    | None      | Warn   |
   ```

   Для конфликтов покажите разрешение:
   ```text
   * Conflict resolution:
     - identity/user-auth spec: Will apply add-oauth then add-jwt (both implemented, chronological order)
   ```

   Для незавершённых изменений покажите предупреждения:
   ```text
   Warnings:
   - add-verify-skill: 1 incomplete artifact, 3 incomplete tasks
   ```

7. **Подтвердите пакетную операцию**

   Задайте пользователю один вопрос о подтверждении:

   - «Archive N changes?» с вариантами на основе статуса
   - Варианты могут включать:
     - «Archive all N changes»
     - «Archive only N ready changes (skip incomplete)»
     - «Cancel»

   Если есть незавершённые изменения, ясно укажите, что они будут архивированы с предупреждениями.

   Маршрутизируйте по намерению в ответе, а не по точной метке — эти метки написали вы,
   поэтому сопоставляйте то, что выбрал пользователь, а не формулировку выше:
   - «Cancel» — остановитесь, не архивируйте. Сообщите, что ничего не было заархивировано, и пропустите оставшиеся шаги.
   - Вариант архивирования всего — продолжите с каждым выбранным изменением, которое не `Blocked`
   - Вариант только готовых — продолжите только с изменениями, которые таблица шага 6 помечает как `Ready` или `Ready*`, и запишите остальные как Skipped в шаге 8d, кроме изменений `Blocked`, которые остаются Failed с `Archive directory already exists`. Если партнёр по конфликту изменения `Ready*` пропущен, заново выведите разрешение этого конфликта, используя только архивируемые изменения.
   - Всё остальное — спросите снова, а не архивируйте

   Перед тем как шаг 8 запишет первую основную спецификацию или переместит какое-либо
   изменение, получите каждый требуемый снимок правил specs для подтверждённого пакета.
   Для каждого изменения, которое будет синхронизировать конкретные
   `artifactPaths.specs.existingOutputPaths`, запустите
   `openspec instructions specs --change "<name>" --json` ровно один раз с теми же
   флагами выбранного корня. Получите все снимки до первой записи или перемещения.
   Если какой-либо запрос завершается с ненулевым кодом или возвращает недопустимый
   JSON инструкций артефакта, определите затронутое изменение, сообщите об ошибке и
   остановите весь пакет до любой записи основной спецификации или перемещения
   изменения. Не считайте сбой запроса пропущенными правилами. Допустимый ответ
   без `rules` — это случай отсутствия правил.

8. **Выполните архивирование для каждого подтверждённого изменения**

   Перед обработкой перенесите записанные решения из шага 5 (после возможного переполучения
   на шаге 7) в два множества по дельтам:
   - `includedDeltas`: все неконфликтующие дельта-спецификации из подтверждённых изменений плюс конфликтные дельты, выбранные для синхронизации
   - `excludedDeltas`: конфликтные дельты из подтверждённых изменений, исключённые из-за отсутствия их реализации
   - Одно изменение может иметь как включённые, так и исключённые дельта-спецификации. Сохраняйте решение по каждой дельте; не сворачивайте его в флаг синхронизации по изменению.

   Обрабатывайте изменения в определённом порядке (с учётом разрешения конфликтов):

   a. **Синхронизируйте включённые дельта-спецификации**:
      - Run the `openspec-sync-specs` workflow inline (agent-driven intelligent merge) только для изменений с записями в `includedDeltas`, передавая только включённые пути дельт и явно указывая игнорировать `excludedDeltas` этого изменения. Дождитесь завершения.
      - Если синхронизация сообщает об условии остановки или блокировки, считайте синхронизацию неудачной. Немедленно прекратите обработку этого изменения. Прежде чем перейти к следующему изменению, запишите результат этого изменения как Failed в результатах пакета, включая условие блокировки/ошибки синхронизации.
      - Не выполняйте послесинхронизационное сравнение содержимого и не перемещайте его `changeRoot`; оставьте изменение нетронутым.
      - Для конфликтов применяйте в разрешённом порядке.
      - Передайте полученный снимок правил specs этого изменения во встроенную синхронизацию; встроенная
        синхронизация должна использовать его повторно без повторного запроса инструкций
      - Применяйте правила артефактов только к основным спецификациям, созданным этим изменением. Они не
        меняют разрешение конфликтов, поведение архивирования или контракты CLI, и их текст не копируется в выходной файл
      - Не делегируйте фоновой задаче — шаг 8c переместил бы `changeRoot` из-под синхронизации, которая всё ещё его читает.
      - Если у изменения нет включённых дельта-спецификаций, не запускайте для него процесс синхронизации.

   b. **Проверьте включённые дельта-спецификации перед перемещением changeRoot**:
      - Повторно выполните сравнение только для дельта-спецификаций из `includedDeltas` с основной спецификацией по пути `<planningHome.root>/openspec/specs/<capability-path>/spec.md` (используйте учитывающий хранилище `planningHome.root` из JSON статуса шага 3, а не жёстко заданный путь репозитория).
      - Проверьте, что основные спецификации обновлены:
        - Добавленные (ADDED) требования присутствуют
        - Изменённые (MODIFIED) требования несут сценарии и изменения описания, названные в дельте, с сохранением их остальных сценариев
        - Удалённые (REMOVED) требования отсутствуют — а там, где эта синхронизация вывела возможность из эксплуатации (удалила её последнее требование, оставив `## Requirements` пустым), её основная спецификация удалена, а не оставлена пустой.
        - Переименованные (RENAMED) требования присутствуют под новым именем и отсутствуют под старым
      - Не проверяйте дельта-спецификации из `excludedDeltas`; они намеренно остаются несинхронизированными.
      - Если синхронизация не удалась или какая-либо возможность не соответствует проверке, сообщите, чем отличается, и не выполняйте/пропустите перемещение `changeRoot` этого изменения — не архивируйте это изменение. `changeRoot` остаётся нетронутым.

   c. **Выполните архивирование**:

      Целевое имя: используйте `<target-name>`, записанное для этого изменения на шаге 3d, без изменений. Никогда не вычисляйте его заново здесь: пакет, работающий за полночь, проверил бы одну дату на шаге 3, а перемещал бы с другой.

      **Проверьте, существует ли уже цель:**
      - Проверьте ещё раз непосредственно перед перемещением, хотя шаг 3 уже проверял: цель может появиться в середине пакета
      - Если да: запишите это изменение как Failed с `Archive directory already exists`, оставьте `changeRoot` на месте, сообщите о любых основных спецификациях, уже синхронизированных для него на шаге 8a, и продолжите с остальными изменениями
      - Если нет: переместите `changeRoot` в каталог архива

      ```bash
      mkdir -p "<planningHome.changesDir>/archive"
      mv "<changeRoot>" "<planningHome.changesDir>/archive/<target-name>"
      ```

      **Убедитесь, что перемещение не создало вложенность:** `mv` завершается с кодом 0 даже когда цель появилась после проверки, перемещая изменение *внутрь* неё. Если `<planningHome.changesDir>/archive/<target-name>/<change-directory-name>` теперь существует (последний сегмент пути `changeRoot`), переместите этот каталог обратно в `changeRoot` и запишите это изменение как Failed с `Archive directory already exists`. Никогда не сообщайте о нём как об архивированном.

   d. **Отслеживайте результат** для каждого изменения:
      - Success: успешно архивировано
      - Failed: ошибка во время архивирования или проверки спецификации (запишите ошибку)
      - Skipped: пользователь решил не архивировать (если применимо)
      - Sync skipped: для каждой дельты из `excludedDeltas` сообщите `sync skipped` с изменением, `<capability-path>` и записанной причиной. Это отличается от пропуска архивирования.

**Предохранители**
- Разрешайте любое количество изменений (1+ допустимо, 2+ — типичный случай)
- Всегда запрашивайте выбор, никогда не выбирайте автоматически
- Обнаруживайте конфликты спецификаций заранее и разрешайте их проверкой кодовой базы
- Когда оба изменения реализованы, применяйте спецификации в хронологическом порядке
- Пропускайте синхронизацию спецификаций только когда реализация отсутствует (предупредите пользователя)
- Показывайте ясный статус по каждому изменению перед подтверждением
- Используйте одно подтверждение для всего пакета
- Никогда не архивируйте после того, как пользователь отменил подтверждение, — отменённый пакет ничего не архивирует
- Отслеживайте и сообщайте все результаты (success/skip/fail)
- Сохраняйте .openspec.yaml при перемещении в архив
- Цель архивирования использует текущую дату, вычисленную один раз на шаге 3d и переиспользуемую при перемещении: YYYY-MM-DD-<name>; имя, уже начинающееся с префикса `YYYY-MM-DD-`, используется как есть (никогда не добавляйте вторую дату)
- Если цель архивирования существует, пометьте это изменение как сбойное, но продолжите с остальными
- Проверяйте каждую цель архивирования на шаге 3, до первой записи основной спецификации; изменение, чья цель существует, никогда не синхронизируется и не перемещается
- Если синхронизация запрошена, run the `openspec-sync-specs` workflow inline (agent-driven) для каждого изменения с включёнными дельта-спецификациями
- Переносите решения по каждой дельте `includedDeltas` и `excludedDeltas` в исполнение; синхронизируйте и проверяйте только включённые дельты
- Сообщайте о каждой исключённой дельте как `sync skipped`, не считая само архивирование пропущенным
- Никогда не архивируйте изменение, пока синхронизация спецификации ещё выполняется, — запускайте синхронизацию встроенно и проверяйте основные спецификации по `<planningHome.root>/openspec/specs/<capability-path>/spec.md` перед перемещением `changeRoot`
- Получайте входные данные архивирования один раз на выбранный корень до проверки спецификаций или перемещений
- Получайте все требуемые снимки правил specs до первой записи основной спецификации или перемещения пакета
- Сбойный запрос входных данных архивирования никогда не блокирует пакет; он продолжается без контекста и указаний
- Сбойный запрос инструкций specs останавливает весь пакет атомарно
- Изменения без конкретных `artifactPaths.specs.existingOutputPaths` продолжаются без синхронизации спецификаций
- Применяйте соответствующий контекст выполнения по всему пакету и сообщайте о конфликтах
- Указания по операциям остаются рекомендательными; рассмотрите каждую запись и объясните отклонённый совет
- Держите входные данные выполнения, анализ конфликтов, значения из CLI и правила артефактов раздельно
- Правила артефактов ограничивают только записываемые спецификации
- Никогда не копируйте текст входных данных выполнения или правил артефактов дословно в выходные файлы
