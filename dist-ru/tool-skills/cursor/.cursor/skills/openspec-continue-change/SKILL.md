Продолжите работу над изменением, создав следующий артефакт.

**Выбор хранилища:** Если пользователь называет хранилище (хранилище — это отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа ведётся в одном из них, запустите `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ, затем передайте `--store <id>` в командах, которые читают или изменяют спецификации и изменения (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора считайте флаг `--store <id>` применённым для остальной части процесса. Каждый пример этих команд без флага ниже — краткая форма: перед запуском добавьте флаг. Например, запускайте `openspec status --change "<name>" --json --store "<id>"`, а не форму без флага, показанную ниже. Другие команды этот флаг не принимают. Подсказки, выводимые командами, уже содержат флаг; сохраняйте его в последующих вызовах. Без хранилища команды работают с ближайшим локальным корнем `openspec/`.

**Проверка проекта:** эти шаги рассчитаны на проект, который уже использует OpenSpec. Перед первым шагом, что-либо записывающим (`new change`, `archive`, `sync specs` или создание файла артефакта), убедитесь, что у проекта есть корень: запустите `openspec list --json` (с `--store <id>`, если выбрано хранилище, поскольку тогда корнем служит хранилище) и прочитайте `root`. Объект root означает, что проект настроен. `"root": null` означает, что нет — здесь нет каталога `openspec/`, и запись вроде `openspec new change` создала бы его как побочный эффект. Команда также завершается с ненулевым кодом — это и есть ответ, а не сбой CLI, поэтому читайте JSON вместо повторных попыток или обходных путей.

Один случай `"root": null` не связан с настройкой: когда сообщение об ошибке `status` начинается с `Declared in` или `Invalid store declaration in` и называет `openspec/config.yaml` (или `config.yml`) этого проекта, проект действительно использует OpenSpec через объявленное им хранилище, которое эта машина не может разрешить (хранилище не зарегистрировано или строка `store:` имеет неверный формат). Не считайте его неинициализированным и не пропускайте ветки ниже: остановитесь перед записью и покажите пользователю `message` и `fix` этой ошибки.

В остальных случаях, при отсутствии корня, дальнейшие действия зависят от того, как был достигнут этот процесс:

- **Автовыбор**: вы сами выбрали этот процесс, не называя пользователь OpenSpec, не называя этот навык и не запуская его слэш-команду. Перестаньте использовать OpenSpec и ответьте на запрос обычным образом, как если бы OpenSpec не был установлен. Не просите его ничего настраивать и не упоминайте настройку OpenSpec.
- **Явный запрос об OpenSpec**: пользователь назвал OpenSpec, назвал этот навык или запустил его слэш-команду. Остановитесь перед записью и спросите, как продолжить: настроить этот проект (`openspec init`), использовать хранилище, которое у него уже есть (`--store <id>`), или продолжить без OpenSpec для этого запроса. Дождитесь ответа.

В обеих ветках никогда не создавайте корень как побочный эффект: не запускайте `openspec init`, пока пользователь сам этого не попросит, не создавайте файлы `openspec/` вручную и не позволяйте команде создавать их.

**Ввод**: можно указать имя изменения. Если оно не указано, проверьте, можно ли вывести его из контекста разговора. Если имя размытое или неоднозначное, вы ДОЛЖНЫ предложить выбрать из доступных изменений.

**Шаги**

1. **Выберите изменение**

   Если имя указано, используйте его. Иначе:
   - Выведите имя из контекста разговора, если пользователь упоминал изменение
   - Выберите автоматически, если существует только одно активное изменение
   - Если выбор неоднозначен, запустите `openspec list --json`, чтобы получить доступные изменения, отсортированные по дате последнего изменения, и предложите пользователю выбрать одно из них

   При запросе выбора предложите 3–4 последних изменённых изменения как варианты, показав:
   - Имя изменения
   - Статус (например, «0/5 задач», «complete», «нет задач»)
   - Как давно оно было изменено (по полю `lastModified`)

   Отметьте последнее изменённое изменение как «(Recommended)», так как, скорее всего, именно его хочет продолжить пользователь.

   Всегда объявляйте: «Using change: <name>» и способ переопределить выбор (например, `/opsx-continue <other>`).

2. **Проверьте текущий статус**
   ```bash
   openspec status --change "<name>" --json
   ```
   Разберите JSON, чтобы понять текущее состояние. Ответ включает:
   - `schemaName`: используемая схема процесса (например, «spec-driven»)
   - `artifacts`: массив артефактов со их статусами («done», «skipped», «ready», «blocked»)
   - `isPlanningComplete`: булево значение, показывающее, завершены ли все артефакты планирования. В более старых версиях CLI то же значение доступно как `isComplete`.
   - `planningHome`, `changeRoot`, `artifactPaths` и `actionContext`: контекст путей и области действия. Используйте их вместо предположения о путях внутри репозитория.

3. **Действуйте в зависимости от статуса**:

   ---

   **Прежде всего завершите частично записанный артефакт**:
   - Артефакт, чей вывод соответствует glob-шаблону (например, `specs/**/*.md`), считывает состояние `done`, как только существует один подходящий файл, поэтому прерванный во время записи его файлов запуск оставляет его в состоянии `done`, когда некоторые файлы ещё отсутствуют
   - Для каждого такого артефакта со статусом `done` сначала получите его инструкции и прочитайте все завершённые зависимости, необходимые для определения ожидаемых файлов. Затем сравните эти файлы с `artifactPaths.<id>.existingOutputPaths`. Для `specs` режима spec-driven прочитайте предложение и проверьте наличие одного файла `specs/<capability-path>/spec.md` на каждую перечисленную в нём возможность; разрешите каждый ожидаемый путь относительно `changeRoot` перед сравнением путей и убедитесь, что каждый из них остаётся внутри `changeRoot` после разрешения символических ссылок — как в его родительских каталогах, так и в самом файле, если он уже существует
   - Никогда не записывайте ожидаемый путь, не прошедший эту проверку; остановитесь и сообщите пользователю. Если какие-то файлы отсутствуют, запишите только недостающие файлы, каждый по своему проверенному пути — когда поле `instruction` делегирует создание навыку или команде, вызывайте его только если он может записать каждый файл по его проверенному пути; иначе остановитесь и сообщите пользователю — и ОСТАНОВИТЕСЬ: это засчитывается как ОДИН артефакт данного вызова. Если вы не можете определить, был ли файл пропущен намеренно, спросите пользователя

   ---

   **Если все артефакты планирования завершены (`isPlanningComplete: true` или устаревшее `isComplete: true`)**:
   - Поздравьте пользователя
   - Покажите итоговый статус, включая использованную схему
   - Предложите: «Планирование завершено! Теперь вы можете реализовать это изменение. Когда реализация и весь отслеживаемый объём работ завершены, заархивируйте его».
   - ОСТАНОВИТЕСЬ

   ---

   **Если есть артефакты, готовые к созданию** (в статусе есть артефакты со `status: "ready"`):
   - Выберите ПЕРВЫЙ артефакт со `status: "ready"` из вывода статуса
   - Получите его инструкции:
     ```bash
     openspec instructions <artifact-id> --change "<name>" --json
     ```
   - Разберите JSON. Ключевые поля:
     - `context`: сведения о проекте (ограничения для вас — НЕ включайте в вывод)
     - `rules`: правила, специфичные для артефакта (ограничения для вас — НЕ включайте в вывод)
     - `template`: структура, которую нужно использовать для выходного файла
     - `instruction`: руководство, специфичное для схемы
     - `resolvedOutputPath`: разрешённый путь или шаблон для записи артефакта
     - `dependencies`: завершённые артефакты, которые нужно прочитать для контекста (записи со `skipped: true` не имеют файлов — не ищите их)
     - `skipped`/`warning`: присутствуют, когда изменение объявляет skip_specs и этот артефакт создавать НЕ нужно — выберите другой артефакт
   - **Создайте файл артефакта**:
     - Прочитайте все завершённые файлы зависимостей для контекста — всегда перечитывайте их с диска, даже если вы видели их ранее в разговоре (пользователь мог их отредактировать)
     - Выберите выходной путь перед созданием чего-либо. Если указанный в инструкциях `resolvedOutputPath` — glob-шаблон, выберите конкретный путь внутри `changeRoot` с помощью инструкции схемы и контекста изменения и убедитесь, что он остаётся внутри `changeRoot` после разрешения символических ссылок — как в его родительских каталогах, так и в самом файле, если он уже существует; если это не так, остановитесь и сообщите пользователю. Иначе выходной путь — `resolvedOutputPath`
     - Если поле `instruction` делегирует создание конкретному навыку или команде, вызывайте его только если он может записать артефакт по этому выходному пути; иначе остановитесь и сообщите пользователю
     - Иначе запишите файл самостоятельно:
       - Используйте `template` как структуру — заполните его разделы
       - Применяйте `context` и `rules` как ограничения при записи — но НЕ копируйте их в файл
       - Запишите файл по этому выходному пути
     - В любом случае убедитесь, что файл артефакта существует по этому выходному пути
   - Покажите, что было создано и что теперь разблокировано
   - ОСТАНОВИТЕСЬ после создания ОДНОГО артефакта

   ---

   **Если ни один артефакт не готов (все заблокированы)**:
   - Этого не должно происходить при корректной схеме
   - Покажите статус и предложите проверить наличие проблем

4. **После создания артефакта покажите прогресс**
   ```bash
   openspec status --change "<name>"
   ```

**Вывод**

После каждого вызова покажите:
- Какой артефакт был создан
- Используемый схемой процесс
- Текущий прогресс (N/M завершено)
- Какие артефакты теперь разблокированы
- Подсказку: «Хотите продолжить? Просто попросите меня продолжить или скажите, что делать дальше».

**Руководство по созданию артефактов**

Типы артефактов и их назначение зависят от схемы. Поле `instruction` из вывода инструкций является авторитетным руководством для каждого артефакта — следуйте ему, даже если артефакт имеет знакомое имя (proposal.md, tasks.md и т.д.), поскольку пользовательские схемы могут определять другое содержимое или другой процесс для тех же имён файлов.

Если поле `instruction` предписывает использовать конкретный навык или команду для создания артефакта, вызовите его вместо прямой записи артефакта — но только после того, как вы выбрали и проверили выходной путь, и только если он может записать файл туда.

**Ограничения**
- Создавайте ОДИН артефакт за вызов
- Всегда читайте артефакты-зависимости перед созданием нового — перечитывайте с диска, а не из памяти разговора (файлы могли измениться с момента последнего просмотра)
- Никогда не пропускайте артефакты и не создавайте их вне порядка
- Если контекст неясен, спросите пользователя перед созданием
- Убедитесь, что файл артефакта существует после записи, прежде чем отмечать прогресс
- Используйте последовательность артефактов схемы, не предполагайте конкретные имена артефактов
- **ВАЖНО**: `context` и `rules` — это ограничения для ВАС, а не содержимое файла
  - НЕ копируйте блоки `<context>`, `<rules>`, `<project_context>` в артефакт
  - Они направляют то, что вы пишете, но никогда не должны появляться в выводе
