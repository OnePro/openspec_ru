Проведите пользователя через его первый полный цикл процесса OpenSpec. Это обучающий опыт — вы будете выполнять реальную работу в его кодовой базе, объясняя каждый шаг.

**Выбор хранилища:** Если пользователь называет хранилище (хранилище — это отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа ведётся в одном из них, запустите `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ, затем передайте `--store <id>` в командах, которые читают или изменяют спецификации и изменения (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора считайте флаг `--store <id>` применённым для остальной части процесса. Каждый пример этих команд без флага ниже — краткая форма: перед запуском добавьте флаг. Например, запускайте `openspec status --change "<name>" --json --store "<id>"`, а не форму без флага, показанную ниже. Другие команды этот флаг не принимают. Подсказки, выводимые командами, уже содержат флаг; сохраняйте его в последующих вызовах. Без хранилища команды работают с ближайшим локальным корнем `openspec/`.

**Проверка проекта:** эти шаги рассчитаны на проект, который уже использует OpenSpec. Перед первым шагом, что-либо записывающим (`new change`, `archive`, `sync specs` или создание файла артефакта), убедитесь, что у проекта есть корень: запустите `openspec list --json` (с `--store <id>`, если выбрано хранилище, поскольку тогда корнем служит хранилище) и прочитайте `root`. Объект root означает, что проект настроен. `"root": null` означает, что нет — здесь нет каталога `openspec/`, и запись вроде `openspec new change` создала бы его как побочный эффект. Команда также завершается с ненулевым кодом — это и есть ответ, а не сбой CLI, поэтому читайте JSON вместо повторных попыток или обходных путей.

Один случай `"root": null` не связан с настройкой: когда сообщение об ошибке `status` начинается с `Declared in` или `Invalid store declaration in` и называет `openspec/config.yaml` (или `config.yml`) этого проекта, проект действительно использует OpenSpec через объявленное им хранилище, которое эта машина не может разрешить (хранилище не зарегистрировано или строка `store:` имеет неверный формат). Не считайте его неинициализированным и не пропускайте ветки ниже: остановитесь перед записью и покажите пользователю `message` и `fix` этой ошибки.

В остальных случаях, при отсутствии корня, дальнейшие действия зависят от того, как был достигнут этот процесс:

- **Автовыбор**: вы сами выбрали этот процесс, не называя пользователь OpenSpec, не называя этот навык и не запуская его слэш-команду. Перестаньте использовать OpenSpec и ответьте на запрос обычным образом, как если бы OpenSpec не был установлен. Не просите его ничего настраивать и не упоминайте настройку OpenSpec.
- **Явный запрос об OpenSpec**: пользователь назвал OpenSpec, назвал этот навык или запустил его слэш-команду. Остановитесь перед записью и спросите, как продолжить: настроить этот проект (`openspec init`), использовать хранилище, которое у него уже есть (`--store <id>`), или продолжить без OpenSpec для этого запроса. Дождитесь ответа.

В обеих ветках никогда не создавайте корень как побочный эффект: не запускайте `openspec init`, пока пользователь сам этого не попросит, не создавайте файлы `openspec/` вручную и не позволяйте команде создавать их.

## Предварительная проверка

Перед началом проверьте, установлен ли openspec CLI:

```bash
# Unix/macOS
openspec --version 2>&1 || echo "CLI_NOT_INSTALLED"
# Windows (PowerShell)
# if (Get-Command openspec -ErrorAction SilentlyContinue) { openspec --version } else { echo "CLI_NOT_INSTALLED" }
```

**Если CLI не установлен:**
> OpenSpec CLI не установлен. Установите его сначала, затем вернитесь к `/openspec-onboard`.

Остановитесь здесь, если CLI не установлен.

## Фаза 1: Приветствие

Отобразите:

```
## Добро пожаловать в OpenSpec!

Я проведу вас через полный цикл изменения — от идеи до реализации — на реальной задаче в вашей кодовой базе. По пути вы изучите процесс, выполняя его.

**Что мы сделаем:**
1. Выберем небольшую реальную задачу в вашей кодовой базе
2. Кратко исследуем проблему
3. Создадим изменение (контейнер для нашей работы)
4. Построим артефакты: предложение → спецификации → дизайн → задачи
5. Реализуем задачи
6. Заархивируем завершённое изменение

**Время:** ~15-20 минут

Начнём с поиска задачи.
```

## Фаза 2: Выбор задачи

### Анализ кодовой базы

Просканируйте кодовую базу в поисках небольших возможностей для улучшения. Ищите:

1. **Комментарии TODO/FIXME** — найдите `TODO`, `FIXME`, `HACK`, `XXX` в файлах кода
2. **Отсутствующую обработку ошибок** — блоки `catch`, которые проглатывают ошибки, рискованные операции без try-catch
3. **Функции без тестов** — сопоставьте `src/` с директориями тестов
4. **Проблемы с типами** — типы `any` в TypeScript-файлах (`: any`, `as any`)
5. **Отладочные артефакты** — `console.log`, `console.debug`, `debugger` в не отладочном коде
6. **Отсутствующую валидацию** — обработчики пользовательского ввода без валидации

Также проверьте недавнюю активность git:
```bash
# Unix/macOS
git log --oneline -10 2>/dev/null || echo "No git history"
# Windows (PowerShell)
# git log --oneline -10 2>$null; if ($LASTEXITCODE -ne 0) { echo "No git history" }
```

### Предложение вариантов

На основе анализа предложите 3-4 конкретных варианта:

```
## Предлагаемые задачи

На основе сканирования вашей кодовой базы вот несколько хороших стартовых задач:

**1. [Наиболее перспективная задача]**
   Расположение: `src/path/to/file.ts:42`
   Объём: ~1-2 файла, ~20-30 строк
   Почему подходит: [краткая причина]

**2. [Вторая задача]**
   Расположение: `src/another/file.ts`
   Объём: ~1 файл, ~15 строк
   Почему подходит: [краткая причина]

**3. [Третья задача]**
   Расположение: [расположение]
   Объём: [оценка]
   Почему подходит: [краткая причина]

**4. Что-то другое?**
   Скажите, над чем вы хотите работать.

Какая задача вас интересует? (Выберите номер или опишите свою)
```

**Если ничего не найдено:** Перейдите к вопросу, что пользователь хочет сделать:
> Я не нашёл очевидных быстрых улучшений в вашей кодовой базе. Что небольшого вы давно хотели добавить или исправить?

### Ограничение объёма

Если пользователь выбирает или описывает что-то слишком крупное (большая возможность, работа на несколько дней):

```
Это ценная задача, но, вероятно, она больше, чем идеально для первого прохождения OpenSpec.

Для изучения процесса лучше меньше — это позволяет увидеть полный цикл, не застревая в деталях реализации.

**Варианты:**
1. **Уменьшить объём** — Какова наименьшая полезная часть [его задачи]? Может, просто [конкретный срез]?
2. **Выбрать что-то другое** — Одно из других предложений или другая небольшая задача?
3. **Всё равно сделать это** — Если вы очень хотите взяться за это, мы можем. Просто учтите, что это займёт больше времени.

Что вы предпочитаете?
```

Разрешите пользователю переопределить, если он настаивает — это мягкое ограничение.

## Фаза 3: Демонстрация explore

После выбора задачи кратко продемонстрируйте режим explore:

```
Прежде чем создавать изменение, позвольте быстро показать вам **режим explore** — именно так вы обдумываете задачи, прежде чем приступать к выбранному направлению.
```

Потратьте 1-2 минуты на исследование связанного кода:
- Прочитайте задействованные файлы
- Нарисуйте быструю ASCII-диаграмму, если это поможет
- Отметьте соображения

```
## Краткое исследование

[Ваш краткий анализ — что вы нашли, какие соображения]

┌─────────────────────────────────────────┐
│   [Необязательно: ASCII-диаграмма]      │
└─────────────────────────────────────────┘

Режим explore (`/openspec-explore`) предназначен именно для такого мышления — исследования перед реализацией. Вы можете использовать его в любой момент, когда нужно обдумать задачу.

Теперь создадим изменение для нашей работы.
```

**ПАУЗА** — Дождитесь подтверждения пользователя перед продолжением.

## Фаза 4: Создание изменения

**ОБЪЯСНИТЕ:**
```
## Создание изменения

«Изменение» в OpenSpec — это контейнер для всего мышления и планирования вокруг объёма работ. Оно находится по пути `changeRoot`, который сообщает `openspec status --change "<name>" --json`, и содержит ваши артефакты — предложение, спецификации, дизайн, задачи.

Создам его для нашей задачи.
```

**ВЫПОЛНИТЕ:** Создайте изменение с производным именем в kebab-case:
```bash
openspec new change "<derived-name>"
```

**ПОКАЖИТЕ:**
```
Создано: <changeRoot из status JSON>

Структура папки:
```
<changeRoot>/
├── proposal.md    ← Зачем мы это делаем (пусто, заполним позже)
├── design.md      ← Как мы это построим (пусто)
├── specs/         ← Подробные требования (пусто)
└── tasks.md       ← Чек-лист реализации (пусто)
```

Теперь заполним первый артефакт — предложение.
```

## Фаза 5: Предложение

**ОБЪЯСНИТЕ:**
```
## Предложение

Предложение фиксирует **зачем** мы делаем это изменение и **что** оно включает на высоком уровне. Это «питч» для работы.

Я составлю его на основе нашей задачи.
```

**ВЫПОЛНИТЕ:** Составьте содержимое предложения (пока не сохраняйте):

`<capability-path>` — это путь директории спецификации относительно `specs/` (например,
`user-auth` или `identity/user-auth`). Используйте точный существующий путь для изменяемых
возможностей. Для новых возможностей следуйте принятой в проекте организации спецификаций.

```
Вот черновик предложения:

---

# Proposal

## Why

[1-2 предложения, объясняющие проблему/возможность]

## What Changes

[Маркированные пункты того, что изменится]

## Capabilities

### New Capabilities
- `<capability-path>`: [краткое описание]

### Modified Capabilities
<!-- Если изменяется существующее поведение -->
- `<existing-capability-path>`: [краткое описание]

## Impact

- `src/path/to/file.ts`: [что меняется]
- [другие файлы, если применимо]

---

Передаёт ли это замысел? Я могу скорректировать перед сохранением.
```

**ПАУЗА** — Дождитесь одобрения/обратной связи пользователя.

После одобрения сохраните предложение:
```bash
openspec instructions proposal --change "<name>" --json
```
Затем запишите содержимое в `resolvedOutputPath` из `openspec instructions proposal --change "<name>" --json`.

```
Предложение сохранено. Это ваш документ «зачем» — вы всегда можете вернуться и уточнить его по мере развития понимания.

Далее: спецификации.
```

## Фаза 6: Спецификации

**ОБЪЯСНИТЕ:**
```
## Спецификации

Спецификации определяют **что** мы строим в точных, проверяемых терминах. Они используют формат требование/сценарий, который делает ожидаемое поведение абсолютно ясным.

Для небольшой задачи нам может понадобиться лишь один файл спецификации.
```

**ВЫПОЛНИТЕ:** Определите, где должен быть создан файл спецификации:
```bash
openspec instructions specs --change "<name>" --json
# Используйте resolvedOutputPath из JSON. Если это glob, выберите конкретный путь файла по инструкции схемы и контексту изменения.
```

Составьте содержимое спецификации:

```
Вот спецификация:

---

# Spec Delta

## ADDED Requirements

### Requirement: <Name>

<Описание того, что система должна делать>

#### Scenario: <Scenario name>

- **WHEN** <условие-триггер>
- **THEN** <ожидаемый результат>
- **AND** <дополнительный результат, если нужно>

---

Этот формат — WHEN/THEN/AND — делает требования проверяемыми. Их буквально можно читать как тестовые случаи.
```

Сохраните в конкретный путь файла, выбранный из `resolvedOutputPath`.

## Фаза 7: Дизайн

**ОБЪЯСНИТЕ:**
```
## Дизайн

Дизайн фиксирует **как** мы это построим — технические решения, компромиссы, подход.

Для небольших изменений он может быть кратким. Это нормально — не каждое изменение требует глубокого дизайн-обсуждения.
```

**ВЫПОЛНИТЕ:** Составьте design.md:

```
Вот дизайн:

---

# Design

## Context

[Краткий контекст о текущем состоянии]

## Goals / Non-Goals

**Goals:**
- [Чего мы пытаемся достичь]

**Non-Goals:**
- [Что явно вне области]

## Decisions

### Decision 1: [Ключевое решение]

[Объяснение подхода и обоснование]

---

Для небольшой задачи это фиксирует ключевые решения без избыточного проектирования.
```

Сохраните в `resolvedOutputPath` из `openspec instructions design --change "<name>" --json`.

## Фаза 8: Задачи

**ОБЪЯСНИТЕ:**
```
## Задачи

Наконец, разбиваем работу на задачи реализации — чек-боксы, которые управляют фазой apply.

Они должны быть небольшими, ясными и в логичном порядке. Каждая группа несёт тесты и документацию для собственной работы — последняя группа предназначена только для интеграционных проверок.
```

**ВЫПОЛНИТЕ:** Сгенерируйте задачи на основе спецификаций и дизайна:

```
Вот задачи реализации:

---

# Tasks

## 1. [Категория или файл]

- [ ] 1.1 [Конкретная задача] — verify: [тест, команда, наблюдаемое поведение или доставленный артефакт]
- [ ] 1.2 [Конкретная задача] — verify: [тест, команда, наблюдаемое поведение или доставленный артефакт]

## 2. Integration Verification

- [ ] 2.1 Verify [более широкая интеграция или поведение системы] with [сквозной тест или наблюдаемый результат]

---

Каждый чек-бокс становится единицей работы в фазе apply. Верна ли такая разбивка на задачи?
```

**ПАУЗА** — Дождитесь одобрения/обратной связи пользователя.

После одобрения сохраните в `resolvedOutputPath` из `openspec instructions tasks --change "<name>" --json`.

Затем спросите:
> "Задачи сохранены. Готовы к реализации?"

**ПАУЗА** — Дождитесь подтверждения пользователя перед реализацией.

## Фаза 9: Apply (реализация)

**ОБЪЯСНИТЕ:**
```
## Реализация

Теперь реализуем каждую задачу, отмечая её по мере выполнения. Я буду объявлять каждую и изредка отмечать, как спецификации/дизайн повлияли на подход.
```

**ВЫПОЛНИТЕ:** Для каждой задачи:

1. Объявите: "Работаю над задачей N: [описание]"
2. Реализуйте изменение в кодовой базе
3. Естественно ссылайтесь на спецификации/дизайн: "Спецификация говорит X, поэтому я делаю Y"
4. Отметьте выполнение в tasks.md: `- [ ]` → `- [x]`
5. Краткий статус: "✓ Задача N выполнена"

Держите пояснения лёгкими — не объясняйте каждую строку кода.

После всех задач:

```
## Реализация завершена

Все задачи выполнены:
- [x] Задача 1
- [x] Задача 2
- [x] ...

Изменение реализовано! Остался один шаг — заархивируем его.
```

## Фаза 10: Архив

**ОБЪЯСНИТЕ:**
```
## Архивирование

Когда изменение завершено, мы архивируем его. Путь архива выводится из `planningHome.changesDir` и даты.

Заархивированные изменения становятся историей решений вашего проекта — вы всегда можете найти их позже, чтобы понять, почему что-то было построено определённым образом.
```

**ВЫПОЛНИТЕ:** Заархивируйте изменение (`--yes` отвечает на запросы подтверждения, на которые вы не можете ответить из вызова инструмента):
```bash
openspec archive "<name>" --yes
```

**ПОКАЖИТЕ:**
```
Архивировано в: `<planningHome.changesDir>/archive/<target-name>/` (целевому имени добавляется сегодняшняя дата в начало, если только имя уже не начинается с префикса `YYYY-MM-DD-` — тогда оно сохраняется как есть, без второй даты)

Теперь изменение является частью истории вашего проекта. Код — в вашей кодовой базе, запись решения — сохранена.
```

## Фаза 11: Итог и дальнейшие шаги

```
## Поздравляем!

Вы только что завершили полный цикл OpenSpec:

1. **Explore** — Обдумали проблему
2. **New** — Создали контейнер изменения
3. **Proposal** — Зафиксировали ЗАЧЕМ
4. **Specs** — Определили ЧТО детально
5. **Design** — Решили КАК
6. **Tasks** — Разбили на шаги
7. **Apply** — Реализовали работу
8. **Archive** — Сохранили запись

Этот же ритм работает для изменения любого объёма — маленького исправления или крупной возможности.
```

## Ограничения

- **Следуйте схеме ОБЪЯСНИТЕ → ВЫПОЛНИТЕ → ПОКАЖИТЕ → ПАУЗА** на ключевых переходах (после explore, после черновика предложения, после задач, после архива)
- **Держите пояснения лёгкими** во время реализации — учите, не читая лекции
- **Не пропускайте фазы**, даже если изменение небольшое — цель в обучении процессу
- **Делайте паузы для подтверждения** в отмеченных точках, но не злоупотребляйте паузами
- **Обрабатывайте выход корректно** — никогда не давите на пользователя, чтобы продолжить
- **Используйте реальные задачи кодовой базы** — не моделируйте и не используйте фиктивные примеры
- **Мягко корректируйте объём** — направляйте к меньшим задачам, но уважайте выбор пользователя
