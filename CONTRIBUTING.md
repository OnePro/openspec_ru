# Участие в разработке openspec_ru

Этот документ описывает, как вносить изменения в перевод OpenSpec, проверять их и выпускать релизы.

## 1. Архитектура переводов (`ru/` → `dist-ru/`)

- Исходники переводов лежат в `ru/` и зеркалируют структуру апстрима `Fission-AI/OpenSpec`.
- `manifest.json` связывает каждый русский файл `ru/...` с его английским путём в апстриме (`en`). Сборка `tools/build-ru.mjs` накладывает `ru/` поверх клона апстрима на закреплённом коммите, собирает проект и кладёт результат в `dist-ru/`.
- `upstream.json` фиксирует пин апстрима: репозиторий, тег (`tag`) и коммит (`commit`). Все переводы сверяются с этим коммитом, а `drift:check` показывает, какие файлы апстрима изменились после перевода.
- **Не редактируйте `dist-ru/` вручную.** Каталог полностью пересоздаётся сборкой и содержит пререндер skills и команд для инструментов, а также `bundle-meta.json`. Любая ручная правка будет перезаписана при следующей сборке. Меняйте файлы в `ru/` и пересобирайте бандл через `npm run build:ru`.

## 2. Правила перевода и терминологии

Терминология — в `glossary.md`, стиль — в `style-guide.md`. Обязательные правила:

**Не переводится:**

- команды `/opsx:*` (и `/opsx-*`), имена команд и их идентификаторы;
- значения `name:` во frontmatter;
- имена файлов `proposal.md`, `design.md`, `tasks.md`, `spec.md`, `SKILL.md` и пути к ним;
- нормативные слова `SHALL`, `MUST`, `WHEN`, `THEN` (в спецификациях они сохраняются латиницей);
- интерполяции `${...}` и подстановки шаблонов в коде.

Заголовки, описания и пояснительный текст переводятся на русский в соответствии с глоссарием.

## 3. Как предложить изменения и проверить их перед PR

Перед открытием PR выполните:

```bash
npm test                                   # юнит- и E2E-тесты
npm run validate:ru                        # проверка всех переведённых файлов
npm run lint:glossary                      # соответствие глоссарию
npm run drift:check                        # какие файлы апстрима изменились после перевода
npm run mark-translated -- <путь> reviewed # отметить файл как проверенный после правки
```

`<путь>` — путь к файлу в `ru/`. Отметку `reviewed` ставит рецензент, который проверил перевод по глоссарию и стилю.

## 4. Правила ведения CHANGELOG.md

- Каждое заметное изменение перевода, патчера или веб-панели добавляется в `CHANGELOG.md` в том же PR.
- Заголовок релиза: `## [X.Y.Z] — YYYY-MM-DD`, например `## [1.15.1] — 2026-11-05`.
- Под заголовком указывается базовый тег апстрима: `> Базовая версия апстрима: Fission-AI/OpenSpec @ v1.15.0 (<коммит>)`.
- Изменения группируются по рубрикам `### Добавлено`, `### Изменено`, `### Исправлено`, `### Синхронизация с апстримом`.
- Подробные правила и пример записи — в начале `CHANGELOG.md`.

## 5. Версионирование MAJOR.MINOR.PATCH и выпуск релизов (`vX.Y.Z`)

- Схема версии: `MAJOR.MINOR.PATCH`. `MAJOR.MINOR` совпадает с `MAJOR.MINOR` тега апстрима из `upstream.json` (сейчас `1.15`), поэтому допустимы `1.15.0`, `1.15.1`, … `1.15.9` и далее `1.15.10+`.
- `PATCH` увеличивается для каждого собственного релиза внутри этой версии апстрима. Если апстрим выпускает новый минор, `MAJOR.MINOR` меняется вместе с `upstream.json`, а `PATCH` начинается с `0`.
- Версия задаётся в двух файлах одновременно: `package.json` и `tools/apply/package.json` (поле `version`). Версия `bundleVersion` в `dist-ru/bundle-meta.json` берётся из корневого `package.json` при сборке.
- Перед тегированием выполните проверку:

```bash
npm run release:check -- --tag vX.Y.Z
```

  Проверка сверяет версии `package.json` и `tools/apply/package.json`, `MAJOR.MINOR` с `upstream.json`, наличие секции `## [X.Y.Z]` в `CHANGELOG.md` и сам тег (`vX.Y.Z` должен равняться `v` + версия из `package.json`).
- После успешной проверки и `npm test` создайте аннотированный тег и отправьте его в `origin`:

```bash
git tag -a vX.Y.Z -m "openspec_ru vX.Y.Z (OpenSpec X.Y)"
git push origin vX.Y.Z
```
