# openspec

> OpenSpec даёт вам и вашему ИИ-агенту для программирования общий проверяемый план ещё до написания кода. Этот файл устанавливает CLI OpenSpec и настраивает ваш проект.

Установите OpenSpec и настройте мой проект. Выполняйте шаги ниже по порядку и останавливайтесь там, где шаг требует остановки.

ЦЕЛЬ: Глобально установить CLI OpenSpec и инициализировать проект пользователя.

КРИТЕРИИ ГОТОВНОСТИ:

- `openspec --version` выводит номер версии
- в подтверждённом пользователем проекте папка `openspec/` создана или обновлена командой `openspec init`
- пользователю сообщён точный синтаксис вызова OpenSpec в его ИИ-инструменте для программирования

СПИСОК ЗАДАЧ:

- [ ] Установить автономный CLI с подтверждения пользователя (npm только как запасной вариант)
- [ ] Проверить, что `openspec` доступен в PATH
- [ ] Подтвердить папку для настройки, затем запустить в ней `openspec init --tools <ids>`
- [ ] Сообщить, что именно создала инициализация и как вызывать OpenSpec

## 1. Установка

Сначала запустите `openspec --version`. Если команда уже выводит версию, CLI установлен: сообщите об этом, запустите `openspec version --check` (она выведет команду обновления для текущего способа установки OpenSpec, если сможет его определить; в противном случае обновите тем способом, которым он был установлен, например `brew upgrade openspec`), предложите выполнить эту команду и переходите к шагу 3. Если установка выполнялась через npm или другой пакетный менеджер, один раз упомяните, что `openspec install` переключает на автономную установку. Только предложите это: пользователь мог выбрать npm намеренно, поэтому не повторяйте предложение и не переключайте способ установки, если он сам не попросит. Никогда не меняйте способ установки самостоятельно — это оставит две конкурирующие копии в PATH.

Установите автономный бинарный файл OpenSpec (на Alpine Linux сначала выполните `apk add libstdc++ libgcc`). Покажите команду для ОС пользователя и запустите её только после подтверждения, затем переходите к шагу 3:

```bash
# macOS / Linux
curl -fsSL https://openspec.dev/cli/install.sh | sh
```

```powershell
# Windows (PowerShell)
irm https://openspec.dev/cli/install.ps1 | iex
```

Если пользователь предпочитает пакетный менеджер или установщик завершился с ошибкой, переходите к шагу 2.

## 2. Пакетный менеджер (только если на шаге 1 установка не выполнена)

Запустите `node --version`. Для установки через пакетный менеджер требуется Node.js 22.12.0 или выше. Если Node отсутствует или его версия старше, не устанавливайте Node, не переключайте версии и не перенастраивайте менеджер версий пользователя самостоятельно; остановитесь и предложите пользователю следующий шаг: https://nodejs.org или, если используется менеджер версий вроде nvm, команду для переключения на более новую версию.

Используйте любой пакетный менеджер, который уже есть в PATH, отдавая предпочтение npm:

```bash
npm install -g @fission-ai/openspec@latest
pnpm add -g @fission-ai/openspec@latest
bun add --global @fission-ai/openspec@latest
yarn global add @fission-ai/openspec@latest   # Yarn 1.x only
```

Не выбирайте пакетный менеджер на основе lock-файла текущего проекта: глобальная установка никак не связана с тем, как устанавливаются зависимости этого репозитория. Если ни один из четырёх вариантов недоступен, остановитесь и сообщите об этом; не импровизируйте с установкой. (На Nix направьте пользователя в раздел Nix документации по адресу https://openspec.dev/docs/installation.)

Покажите точную команду и получите подтверждение перед её запуском; это устанавливает ПО вне проекта, и пользователь может предпочесть другой пакетный менеджер для управления им.

Остановитесь и спросите снова, если установка требует прав sudo или администратора, завершается с ошибкой доступа или сообщает, что глобальная директория bin отсутствует или не настроена. Никогда не редактируйте стартовые файлы оболочки (.bashrc, .zshrc, .profile, fish, профиль PowerShell) и никогда не запускайте команды настройки, которые их изменяют; покажите изменение и позвольте пользователю внести его самостоятельно.

## 3. PATH

Запустите `openspec --version`. Если команда не найдена, возможно, она отсутствует только в текущей оболочке: сообщите, куда она была установлена (автономный установщик выводит папку, по умолчанию `~/.local/bin`; у пакетного менеджера своя глобальная папка bin) и как добавить эту папку в PATH для оболочки и ОС пользователя, затем остановитесь и дождитесь подтверждения. На Windows автономный установщик сам добавляет свою папку в пользовательский PATH; новый терминал подхватит изменения. Если выводится более старая версия, чем та, о которой только что сообщил установщик, значит, более ранняя копия перекрывает её в PATH; сообщите обе версии вместо того, чтобы продолжать. Если пользователь использует менеджер версий, укажите на это вместо редактирования PATH в обход него: в nvm или fnm CLI привязан к версии Node, активной на момент установки, а в asdf или volta может потребоваться перегенерация шима (shim).

## 4. Инициализация

Определите, где должна находиться папка `openspec/`, и начните со своего лучшего предположения, а не с открытого вопроса: корень проекта, в котором работает пользователь, почти всегда является правильным местом. Назовите выбранную папку и дайте возможность скорректировать её, например: «вы находитесь в ~/code/acme-api, поэтому я настрою OpenSpec там». Отдавайте предпочтение корню системы контроля версий перед текущей директорией, а в монорепозитории укажите, какой пакет вы выбрали и почему. Чтобы указать папку, отличную от текущей, передайте путь к ней: `openspec init <path> --tools <ids>`.

Команда init создаёт `openspec/` там, куда вы укажете, и не предупредит, если место выбрано неверно. Если папка является домашней директорией, временной директорией или вообще не содержит проекта, остановитесь и спросите, где находится проект.

Затем определите, с какими ИИ-инструментами для программирования работает пользователь, и снова начните с предположения вместо открытого вопроса: вы, скорее всего, уже запущены внутри одного из них, поэтому назовите его и спросите, что ещё используется, предложив несколько распространённых вариантов (Claude Code, Cursor, Copilot, Codex). Объясните, на что влияет ответ: каждый названный инструмент получает собственные файлы навыков (skills) и команд в проекте, а повторный запуск init позже позволит добавить новые, поэтому короткий список сейчас ни к чему не обязывает. Сопоставьте каждый инструмент с идентификатором из `openspec init --help` (Copilot — это `github-copilot`, Zoo Code — `roocode`). Флаг `--tools` принимает список через запятую, поэтому укажите их все.

Команда `openspec init --tools <ids>` автоматически и без предупреждения удаляет остатки старых версий OpenSpec, включая файлы промптов `opsx-*.md` в домашней директории (Codex хранит их в `~/.codex/prompts`). Перед запуском проверьте их наличие: папки `.../commands/openspec/`, маркерные блоки OpenSpec в файлах вроде CLAUDE.md или AGENTS.md и промпты `opsx-*.md` в домашней директории. Перечислите всё найденное, прямо скажите, что init удалит эти файлы, и дождитесь разрешения; если ничего не найдено, сообщите об этом и продолжайте без дополнительных вопросов. Существующая папка `openspec/` не является проблемой: init обновит её, не трогая спецификации и изменения.

Затем запустите: `openspec init --tools <ids>`, добавив путь, если целевая папка не является текущей.

## 5. Отчёт

Не стройте предположений о том, что должно было появиться; передайте то, что реально вывела команда init: сколько навыков (skills) и/или команд она создала и где, строку с файлом конфигурации, любые примечания «Setup required», а также что нужно перезапустить или перезагрузить. Некоторые инструменты поддерживают только навыки и корректно создают ноль файлов команд, поэтому отсутствие команд само по себе не является ошибкой. Если команда init сообщила, что ничего не было сгенерировано, передайте предложенное ею решение вместо повторных попыток.

В завершение сообщите пользователю, как вызывать OpenSpec в его инструменте, взяв точное написание из созданных при инициализации файлов, а не из итоговой строки отчёта: пунктуация зависит от инструмента (`/opsx:propose` в одних, `/opsx-propose` в других, `@opsx-propose` в Amazon Q), а инструменты, получающие навыки вместо команд, вызываются по имени навыка (`/openspec-propose`, или `$openspec-propose` в Codex, или `/skill:openspec-propose` в Kimi Code).
