# docs-lab: параллельная пересборка документации OpenSpec

**Статус: текст появляется страница за страницей; остальное — скелеты** (настоящие заголовки плюс однострочное утверждение о назначении через `>`, которое сайт поднимает в описание страницы). Живой сайт собирается из этого дерева: `website/docs.sync.config.mjs` сопоставляет эти файлы с опубликованными страницами, а старое дерево `docs/` сайтом больше не используется.

Этот README отвечает за структуру: какие страницы существуют и чему учит каждая из них. Обратное представление — от назначения или тезиса к странице, которая за него отвечает, — находится в [message-map.md](message-map.md). То, как их писать (стиль, тон, форматирование), описано в навыке `write-openspec-docs` в файле [writing.md](../.agents/skills/write-openspec-docs/writing.md).

## Планка качества для каждой страницы

Каждая страница в docs-lab пишется вручную, с нуля. Старое дерево `docs/` служит источником фактов, но текст оттуда никогда не переносится.

Наша цель — чтобы читатель уловил суть: каждая страница легко читается и понятна любому человеку независимо от уровня подготовки, а главное — она простая. Худшее, что мы можем выпустить, — это документация, требующая высоких когнитивных затрат на понимание; эта цена складывается из сложных слов, неудачных метафор, случайной терминологии без пояснений и форматирования, которое мешает чтению. У каждого предложения есть цель, оно легко читается и воспринимается. Если предложение не проходит эту проверку, перепишите или удалите его.

## Правила структуры

**Папки — это разделы.** Каждая страница живёт в папке своего раздела (`start/`, `guides/`, `customize/`, `multi-repo/`, `reference/`, `help/`); в корне лежат только этот README, `message-map.md` и `sources.md`. Большинство папок публикуются как одна группа боковой панели; `guides/` публикуется как группа Guides, содержащая три сворачиваемые подгруппы (Основы OpenSpec, Использование OpenSpec, Внедрение OpenSpec), которые по умолчанию развёрнуты (скрыты с сайта, пока страницы не написаны: весь раздел закомментирован в `website/docs.sync.config.mjs`, а ссылки на руководства ведут на их исходники на GitHub, пока раздел не вернут в список). Раздел Reference содержит три вложенные папки (`reference/architecture/`, `reference/schemas/` и `reference/configuration/`), каждая из которых публикуется как сворачиваемая группа с `index.md` в качестве посадочной страницы; схема spec-driven публикуется как одна страница (`reference/schemas/spec-driven/index.md`) внутри группы Schemas. Названия и URL берутся из `website/docs.sync.config.mjs`, поэтому перемещение файла никогда не меняет URL.

**Обучайте один раз.** У цикла (предложить, проверить, применить, отправить в архив) есть один источник обучения; все остальные страницы ссылаются на него и никогда не объясняют заново:

- `start/quickstart.md` обучает циклу с точки зрения UX: как человек проводит изменение по жизненному циклу, включая то, что архив делает на диске.
- `start/overview.md` показывает его как презентацию: только текст, без объяснений.
- `guides/concepts.md` не касается цикла: страница объясняет артефакты (спецификации, изменения, дельту) и ссылается на быстрый старт для изучения цикла. Пути на диске приводятся в тексте рядом с понятием, к которому они относятся, и никогда не выделяются в отдельный раздел о структуре папок.
- `start/installation.md` отвечает за установку; `start/setup.md` отвечает за инициализацию и то, что она записывает. Быстрый старт начинается с одной строки предварительных требований, ссылающейся на обе страницы, и стартует с исследования.

**Руководства против справочника.** `reference/skills.md` содержит контракт каждого навыка: аргументы, что он создаёт и чем отвечает. Страницы руководств (подгруппы Using и Adopting) отвечают за принятие решений человеком при выполнении задачи, включая то, когда к какому навыку обращаться; они могут охватывать несколько навыков и никогда не повторяют механику их работы. `reference/architecture/` — единственное исключение из правила «справочник только для быстрого поиска»: это объясняющий материал, размещённый здесь из прагматических соображений, пока он состоит из трёх страниц. Если он разрастётся (например, вобрав внутреннее устройство для контрибьюторов), стоит выделить ему собственную папку и вкладку.

**Справочник предназначен для быстрого поиска и назван соответственно.** `reference/schemas/` и `reference/configuration/` — это контракты: ключи, значения, типы, значения по умолчанию и расположения, оформленные в виде таблиц и блоков кода. Всё объясняющее (что такое схема, что поместить в config.yaml) живёт в разделах Customize или Guides; на такие материалы даются ссылки, они никогда не пересказываются. Именование следует трём правилам. Посадочная страница папки справочника называется «Обзор»; метка папки уже называет группу, и повторение создаёт двойную вложенность в боковой панели. Страница, документирующая один файл, содержит в заголовке понятие и имя файла (сначала понятие), где понятие указывает на назначение файла, а не просто на область его действия («Конфигурация проекта (config.yaml)», «Настройки CLI (config.json)»): левый край — это то, по чему глаз различает пункты в боковой панели, а имя файла в заголовке соответствует тому, что читатели ищут и видят на диске. Файл, имя которого само является используемым читателями термином, сохраняет в качестве заголовка только имя файла (`schema.yaml`); страница, отвечающая за один продуктовый термин, берёт этот термин в качестве заголовка (`spec-driven`); а страница, охватывающая несколько файлов, берёт только само понятие (Хранилища), перечисляя свои файлы в строке назначения.

**FAQ состоит из однострочников.** Каждая запись в FAQ — это короткий ответ максимум в несколько строк или ссылка-маршрутизатор на страницу, которая отвечает за тему. Инструкции о том, как что-то сделать, никогда не живут в FAQ: когда ответ перерастает однострочный формат, он переезжает в руководство или справочник, а запись в FAQ превращается в указатель.

## Старая документация

Дерево `docs/` устарело, и по плану мы удалим его, как только docs-lab покроет всё его содержимое. Оно превратилось в свалку некачественного ИИ-текста, поэтому ничто оттуда не переносится как готовый текст (см. раздел «Планка качества для каждой страницы»). До самого удаления оно остаётся нетронутым: исправления вносятся в docs-lab, и никогда — в `docs/`.

Файл [`sources.md`](sources.md) сопоставляет каждую текущую страницу `docs/` с её местом назначения здесь: это исходный материал во время написания черновиков и список перенаправлений при переключении. Шаги переключения описаны в разделе [Cutover](sources.md#cutover) этого файла.

- Не начато: страница `start/overview.md` намеренно пуста. 2026-08-21 мы очистили скелет (заголовки, сюжетные опорные точки, галерею диаграмм), чтобы переписать посадочную страницу с нуля. Старая подача («общий проверяемый план до написания кода») недостаточно хорошо продаёт OpenSpec сейчас, когда режим планирования есть везде; переписанный вариант должен делать ставку на то, чтобы крупные функции развивались по плану и оставались согласованными (команды, нативность для git, задуманное поведение против реализованного, концепция контура управления). Бриф находится в `Notes.md` («Start > Overview»); варианты диаграмм ушли вместе с галереей и сохранились в истории git. Пока новый текст не готов, страница убрана с сайта: её запись закомментирована в `website/docs.sync.config.mjs`, а `/docs` перенаправляет на Installation (`website/public/_redirects` плюс резервный вариант в маршруте страницы документации). Чтобы вернуть её, достаточно раскомментировать одну строку и удалить два перенаправления. Правило «Обучайте один раз» по-прежнему действует: цикл упоминается здесь только как презентация.
- Обратная связь по продукту, не задача документации: поле `instruction` для дизайна в схеме spec-driven перечисляет шесть разделов (включая Migration Plan и Open Questions), но `schemas/spec-driven/templates/design.md` содержит только четыре заголовка. Документация показывает оба варианта дословно; несоответствие нужно исправлять в самом продукте. Отмечено 2026-08-14 при консолидации страницы spec-driven.
- Обратная связь по продукту, не задача документации: `openspec store setup --remote` записывает URL в `store.yaml`, но никогда не настраивает `origin` в git, поэтому инструкция «выполните setup --remote, а затем `git push -u origin main`» в таком виде завершается ошибкой; вместо этого на странице Stores показано `git remote add`. Готовое для вставки исправление отсутствующего хранилища в `openspec doctor` работает на основе удалённых репозиториев из `references:`, а не `store.yaml`. Отмечено 2026-08-21 при переносе страницы Stores.
- Доработка руководства по стилю (`.agents/skills/write-openspec-docs/writing.md`) по итогам ревью страницы Stores от 2026-08-21: никогда не используйте термин, который страница ещё не показала (говорите «строка `store:`», а не «указатель»; давайте определение, сначала показывая артефакт); когда поведение зависит от начального состояния читателя, перечислите состояния и проследите каждое до его результата; подлежащими в предложении выступают «вы», «OpenSpec» или «ваш агент», но никогда не модуль реализации («резолвер выбирает») и не класс сущностей («проекты только с хранилищем делают...»); когда определённый ранее термин повторно используется через раздел, кратко напомните его смысл в скобках в месте использования.
